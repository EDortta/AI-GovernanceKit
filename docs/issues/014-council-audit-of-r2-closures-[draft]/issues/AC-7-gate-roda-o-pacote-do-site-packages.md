# Issue AC-7 — origem: concílio de fechamentos, 2026-08-13 (lentes: sweep skeptic + migrator, independentes)

## AC-7 — o gate valida com uma versão que não é a do repositório, e sai 0 [alta]

### Contexto

O achado `6bb1027e#4` era: *"os dois `--check` usavam caminho relativo: o gate era no-op
silencioso fora da raiz do repositório"*. O fechamento resolveu **os dois `--check`**
contra `$HERE`.

As **duas linhas seguintes do mesmo arquivo** não foram tocadas
(`scripts/validate-governance.sh:26-27`):

```sh
python3 -m governancekit.cli …
```

`python3 -m` resolve o módulo por `cwd`/`sys.path`. De `/tmp`, carrega o
`governancekit` **instalado** em `~/.local/lib/python3.10/site-packages` — não o do
repositório onde o script vive. E o kit se instala como wheel por decisão de projeto,
então "há um wheel mais velho instalado" é o estado **normal** do parque.

O gate roda um `doctor` de outra versão, sem os checks que a entrega acabou de criar, e
sai `rc=0`.

### Reprodução

```
$ cd /tmp && bash …/scripts/validate-governance.sh $T
snapshot is current for v1.2.1
LLM catalog is current with …          # os --check corrigidos: OK
{"ok": false, "checks": [...]}          # 25 checks, NENHUM "§Sending Email contract"
rc=0
$ cd /tmp && python3 -c 'import governancekit; print(governancekit.__file__)'
/home/esteban/.local/lib/python3.10/site-packages/governancekit/__init__.py
$ python3 -c "from governancekit import doctor; print(hasattr(doctor,'_check_sending_email_contract'))"
False        # no repositorio (HEAD): True
```

Mesmo script, mesmo alvo, dois `cwd`, **dois vereditos diferentes** — inclusive na
mensagem de remédio, que de `/tmp` sai na versão pré-`ade371f5#8`.

### Objetivo

Que o gate valide sempre com o código do repositório onde o script vive, de qualquer
`cwd`, e que a divergência seja impossível de passar despercebida.

### Escopo

- As duas invocações resolvem o pacote contra `$HERE` — `PYTHONPATH` explícito, ou
  executar o `cli.py` por caminho, ou `python3 -c` com `sys.path` semeado. A forma menos
  frágil é escolha da implementação.
- Varrer **todos** os scripts em `scripts/` pela mesma classe: `python3 -m`, caminho
  relativo, dependência implícita de `cwd`. O achado original e este são a mesma coisa
  duas linhas adiante; a terceira vez não pode acontecer.
- O script imprime qual `governancekit` está usando. Um gate que não diz o que executou
  não é auditável.
- **Teste de regressão.** Este achado e o original foram fechados por reprodução, o que
  o §2 aceita — mas reprodução fecha o achado e não protege contra recorrência. Ver
  `AC-19` e a pergunta 4 do RESUME.

### ARO

- **Assumption**: o script deve validar o repositório onde mora. Se a intenção fosse
  validar o wheel instalado, o comportamento seria correto e a issue é de documentação —
  mas então os dois `--check` corrigidos estariam errados, o que ninguém sustenta.
- **Risk**: forçar `$HERE` no `sys.path` muda o que o gate valida em hosts onde só o
  wheel existe. Mitigação: o script mora no repositório; se o repositório está lá, é ele
  que manda.
- **Risk**: um teste que executa o script precisa de um alvo, e `verify-elo4.sh` faz
  `git init` — cuidado para o teste não escrever perto do worktree.
- **Owner**: a definir.

### Plano de teste

- Rodar o script de três `cwd` diferentes ⇒ saída idêntica, e o `governancekit` usado é
  o do repositório nos três.
- Wheel instalado propositalmente divergente ⇒ o gate ainda vê os checks do repositório.
- Mutação: voltar `python3 -m` sem `PYTHONPATH` ⇒ teste vermelho.
- Varredura dos demais scripts registrada.

### DoD

- O gate é independente de `cwd`, provado por teste, não por reprodução.
- O script declara qual runtime executou.
- A varredura por `python3 -m` e caminhos relativos em `scripts/` está feita e escrita.
